#### 1. Задача (оформление и орфография от авторов задания)

```
	Цель: реализовать backend-приложение для управления пользователями, начислением наград и отложенными задачами.

	Стек технологий
	
	 - Django REST Framework
	 - PostgreSQL
	 - Celery
	 - Redis (как брокер для Celery)
	 - JWT
	 - CORS и CSRF (по стандартам безопасности)
	
	
	Функциональность
	
	Аутентификация
	- Настроить авторизацию по JWT
	 - Эндпоинты:
	   POST /api/token/ — получение access/refresh
	   POST /api/token/refresh/ — обновление
	   POST /api/token/verify/ — валидация токена
	 - Настроить CORS для доступа с фронта (можно указать localhost:3000)
	 - Настроить CSRF для админки (по желанию)
	 
	Пользовательская модель
	- Расширить AbstractUser
	 - Добавить поле coins: IntegerField (по умолчанию 0)
	 
	Админка
	- Возможность создавать пользователя
	 - Возможность создавать награду (см. ниже)
	 
	API: Получение информации о себе
	- GET /api/profile/
	 - Только для авторизованных пользователей
	 - Ответ: username, email, coins
	 
	Модель ScheduledReward
	- Поля:
	   - user (ForeignKey)
	   - amount (целое число)
	   - execute_at (дата/время)
	 - Цель: планирование награды, которая должна быть выдана позже
	
	Celery: обработка ScheduledReward
	- Настроить Celery и Redis
	 - При создании объекта ScheduledReward → планируется задача
	 - В execute_at:
	   - начисляется coins пользователю
	   - создаётся запись в RewardLog
	   
	Модель RewardLog
	- Поля:
	   - user
	   - amount
	   - given_at

	API: Список наград
	- GET /api/rewards/
	 - Возвращает список всех выданных наград пользователю
	 
	(Дополнительно) POST /api/rewards/request/
	- Пользователь может сам запросить награду
	- Ограничение: только 1 раз в сутки
	- При успешном запросе создаётся ScheduledReward, которая выполнится через 5 минут
```

### Результаты

#### TL;DR

Для запуска необходимо обеспечить присутствие в корневой папке проекта файла `.env` аналогичного по структуре [.env.example](./.env.example), после чего выполнить команду

```bash
	docker compose up [-d]
```

Параметр `-d` является опциональным, применяется для запуска контейнеров в [detached-режиме](https://docs.docker.com/engine/containers/run/#foreground-and-background/).

Миграции БД накатываются автоматически при запуске контейнера с сервисом. Для персистентного хранения данных БД между запусками сервиса организован именованный Docker volume.

Необходимая по условиям выполнения тестового документация Swagger доступна по адресу [http://127.0.0.1:8000/swagger/](http://127.0.0.1:8000/swagger/).

В ТЗ не оговорена реализация эндпоинта API для начисления награды пользователю. Поэтому работа с соответствующими моделями реализована в панели администратора по адресу [http://127.0.0.1:8000/admin/](http://127.0.0.1:8000/admin/). Логин и пароль суперпользователя для доступа в панель администратора задаются в `.env` в переменных `DJANGO_SUPERUSER_USERNAME` и `DJANGO_SUPERUSER_PASSWORD`.

#### Подробнее

Тестовое задание выполнено в соответствии с поставленной задачей.

Во исполнение одного из условий была реализована JWT-авторизация с помощью плагина [django-rest-framework-simplejwt](https://github.com/jpadilla/django-rest-framework-simplejwt/).

Стандартным алгоритмом шифрования при создании и валидации токена для данного плагина является симметричный HS256. Вместо него реализовано использование асимметричного RS256, публичный и приватный ключи для него генерируются при запуске контейнера, что повышает безопасность данных за счет минимизации возможности утечки указанных ключей в условиях изоляции контейнера.

CORS настроен в соответствии с заданием, использовано Django-приложение [django-cors-headers](https://github.com/adamchainz/django-cors-headers/).

CSRF-защита реализована с помощью стандартного Django-middleware и фактически используется только при авторизации в панели администратора через форму в шаблоне. Для API авторизация реализована только через JWT, в связи с чем дополнительные меры защиты от CSRF-атак нецелесообразны.

Модели реализованы в соответствии с заданием. 

Создание задачи для Celery при создании объекта класса `ScheduledReward` реализовано с помощью [сигнала](https://docs.djangoproject.com/en/5.1/topics/signals/). Исполнение задачи происходит при наступлении установленного в объекте времени.

В качестве брокера для Celery использован Redis, он же использован в качестве кэша при выполнении дополнительного пункта ТЗ для реализации ограничения срока хранения данных, создаваемых при обработке запроса, поступающего по адресу [/api/rewards/request/](http://127.0.0.1:8000/api/rewards/request/) 

В качестве wsgi-сервера использован [uWSGI](https://uwsgi.readthedocs.io/en/latest/).

Поскольку данное задание является **тестовым** и не предполагает выхода в продуктовую среду, при его выполнении опущены некоторые стандартные для индустрии шаги, как, например, реализация обратного прокси на Nginx с делегированием ему раздачи статики, ограничение доступа к контейнерам напрямую через закрытие портов с хостом и т.д.

По этой же причине код снабжен подробными комментариями[^1], которые разъясняют нюансы и детали реализации тех или иных компонентов приложения.

По условиям задачи не требовалось, в качестве инициативы автора код покрыт тестами с помощью pytest.
